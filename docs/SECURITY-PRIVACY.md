# Security and privacy

What the stack collects, who can reach it, how long it should live, and the
costs the architecture imposes — stated rather than buried.

---

## Data inventory

| Field | Sensitivity | Held by | Retention |
|---|---|---|---|
| Email address | identifying | Drupal + all four applications | event + audit period |
| Name | identifying | Drupal + all four | event + audit period |
| Home institution | low | Drupal, reconciler, nametags, gallery | event + audit period |
| Attendee status | low | Drupal, reconciler, nametags, lodging | event + audit period |
| Student | low | Drupal, reconciler, nametags, lodging | event + audit period |
| Dietary restrictions | **implies religion or health** | **Drupal only** | delete once catering is confirmed |
| T-shirt size | low, but body data | Drupal, reconciler | delete after distribution |
| Poster title, adviser, abstract | **public by intent** | Drupal, gallery | published; kept as the record |
| Lodging required | low | Drupal, lodging | T+30 days |
| **Gender identity** | **sensitive** | Drupal, lodging | **T+30 days** |
| **Roommate preference** | **sensitive** | Drupal, lodging | **T+30 days** |
| **Identified roommate** | **sensitive** | Drupal, lodging | **T+30 days** |
| **Passport number, DOB, country of issue, expiry** | **highest** | **Drupal only — never in any application** | **purge on a schedule** |
| Payment amount and status | financial | Drupal (slug only), reconciler | audit period |
| Card details | — | **nowhere. Eventbrite holds them.** | — |

**No card data ever touches these applications.** The reconciler sees an amount
and a status, never a payment instrument.

**Passport data never leaves Drupal.** The travel form emails it to an agency in
plaintext HTML. That is what was done; it is not a recommendation. See
[the privacy note](https://github.com/pu-shd/drupal-event-forms/blob/main/docs/PRIVACY.md)
before importing that form, and prefer sending attendees to the agency's own
secure portal.

**Dietary restrictions are not low-sensitivity.** "No pork", "coeliac" imply
religion or a medical condition. They deliberately reach no application: export
once for the caterer, then delete the export.

## The three sensitive lodging fields

Gender identity, roommate preference and identified roommate are collected for
one purpose, are useful for about three weeks, and are the fields most likely to
cause real harm if they leak.

- They reach **one** application. Do not add them to a contract for another.
- Access to `lodging-planner` is a smaller list than access to the reconciler.
  Keep it that way; `AUTHORIZED_PRINCIPALS` is per application for this reason.
- Delete at T+30 days, including from the final backup.

If you are not making room assignments yourself, do not collect them at all.

## Authentication

**Azure Easy Auth in front of every admin route**, plus an allow-list. There is
no application-level login, no password store, no session table.

- An **empty allow-list denies everyone**, deliberately. An empty list meaning
  "allow all" would turn one mis-set application setting into an open admin
  panel. This has surprised people; it is the right surprise.
- The application requires **both** the `X-MS-CLIENT-PRINCIPAL-NAME` header and
  the base64 claims blob, and cross-checks them. Trusting one header meant that
  anything able to reach the container other than through the front door had a
  complete authentication bypass.
- A dev bypass **refuses to start** when `WEBSITE_SITE_NAME` is set. One
  mis-set setting cannot grant admin to anyone sending a header.

The predecessor trusted a single spoofable header at eighteen call sites, each
of which had to remember to call the check. It is now a `Depends` on the router,
which cannot be forgotten by the next handler somebody adds.

## Public write surfaces

There are none, except token-verified webhooks.

`POST /api/admin/clear` used to be deliberately unauthenticated so a scheduled
workflow could curl it. Anyone who knew the path could erase every registration
and payment. The route is gone; destructive operations now run inside the
container over an Azure-authenticated channel with required reviewers.

## Webhook tokens

One per application, compared with `hmac.compare_digest`, generated by the
deployment toolkit. Never logged: the log line is
`webhook.verify outcome=deny reason=mismatch fp=3f9a21`, a six-character
fingerprint of what was presented.

The predecessor logged the received token **and the expected token** at INFO on
every call, so both sat in the App Service log stream and Log Analytics,
readable by anyone with Reader on the resource group.

**Rotating one has a gap and Drupal does not retry.** Between changing the
application setting and updating the Drupal handler, submissions 403 and are
lost to the application. Rotate outside a registration window.

**Any Drupal admin can read every token.** They are handler configuration in
plain text. That is the real trust boundary, and it is acceptable only while the
Drupal admins and the event administrators are the same people.

## Fragment versus query

`#fragment` parameters are never sent to a server — not to access logs, not in
`Referer`, not through a proxy. `?query` parameters are sent, and land
everywhere.

`link-forge` makes each link kind declare `param_style` and `sensitivity`, and
**refuses** to render a bearer credential in a fragment (which would not work) or
to hand over a `query` + `pii` link without a warning banner.

Tokenized prefill links are bearer credentials: the holder can open and edit that
person's submission. Nine leaked once through a saved HTML page. Never commit
one, never put one in a shared document, rotate after the event.

## A backup download is a full personal-data export

`GET /api/admin/db-backup` returns every row of every table. For
`lodging-planner` that includes the three sensitive fields.

Treat the file as you would a spreadsheet of attendee passports: a storage
account with restricted access, not a Slack thread and not a downloads folder.

Restore is **off by default** (`ENABLE_RESTORE=False`) and requires a principal,
the flag, a confirmation phrase, and a pre-restore snapshot. It truncates every
table.

## The cost of independent databases: a deletion request is a five-database pass

This is the price of the architecture and it is not hidden.

1. `ticket-reconciler` — registrant, payments, check-in state, swag issuance
2. `nametag-press` — registrant, badge cache
3. `lodging-planner` — attendee, room assignment, **and roommate references in
   other people's records**
4. `poster-gallery` — presenter, if they presented. Whether a published abstract
   stays as the record of the event is a conversation, not an assumption
5. Drupal — the submission. Last, because until then it is how you find their
   `person_key`
6. **Backups.** A deletion that leaves the person in last night's snapshot is not
   a deletion

`link-forge` holds nothing, which is exactly why it holds nothing.

`eventkit`'s `person_key` makes step 1–4 a lookup rather than a search, and each
application has an `identity-drift` command for checking a population against
another application's backup. Budget an hour and write down what you did.

## Incident checklist

**A webhook token may have leaked**
1. Rotate the application setting.
2. Update the Drupal handler. Keep the window to seconds; submissions in between
   are lost to the application, though Drupal retains them.
3. Check `rejected_total` at `/api/webhook/status` afterwards.
4. Replay any missed submissions from Drupal — each application re-accepts the
   same `uuid` idempotently.

**A prefill token may have leaked**
1. Regenerate that submission's token in Drupal; the old link dies.
2. Assume the submission was read and possibly edited. Diff it.

**A backup file may have leaked**
Treat as a full attendee-data breach and follow your institution's process. It
contains everything.

**Admin sign-in returns 500 and nothing changed**
The Easy Auth client secret expired. `eventkit azure secrets rotate` — it uses
`--append`, so there is no window. The nightly drift job warns 60 days out; if
you are reading this, it was not running.

## What is deliberately not here

- **No secret scanner, no third-party CI actions.** Secret detection is `grep`
  over specific credential shapes, verified in both directions: it fires on
  planted secrets and stays quiet on `password = os.environ[...]`. One less
  dependency in the path that produces a shipped artifact.
- **No card handling.** Eventbrite is the merchant of record.
- **No SSO beyond Easy Auth.** Adding a second authentication path doubles the
  ways in.
